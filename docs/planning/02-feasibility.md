# What works on a GitHub profile

Research snapshot, November 22, 2026. The browser measurements below used the checked-in asset at commit `87436ed`. They are reproducible observations from one desktop browser.

## Where the keyboard can go

GitHub converts README markup to HTML, sanitizes it and applies image and link filters. The browser then loads this repository’s SVG through an HTML image element. In that mode the SVG can paint and run time-based declarative animation. Its internal links, input events, scripts and externally loaded game engines are unavailable. A form inside SVG foreignObject inherits those restrictions. Changing the SVG host or compiling a game to WASM leaves the embedding mode the same. Opening a standalone HTML document changes the execution context. A normal HTML anchor around the README image is the simplest bridge. [GitHub’s rendering pipeline](https://github.com/github/markup#github-markup) · [SVG 2 processing modes and embedding examples](https://www.w3.org/TR/SVG2/conform.html#processing-modes)

A remote server that returns changing images still receives image requests, not keystrokes. A shell server would add latency and privileges for operations that a local directory map can represent. A disclosure widget can reveal prewritten README content, but cannot steer a game.

## Does byte order improve the reveal?

The committed SVG is 753 × 1462 units, 1,238,428 bytes on disk and 128,128 bytes with Node gzip level 9. That last figure is a reproducible comparison metric. Actual transfer size depends on content encoding and cache. The first prompt precedes the expensive island groups in the current document order.

**Controlled stall.** Served HTML from localhost with a white background and an explicitly sized image. Served the actual SVG uncompressed, flushed its prefix through the first closing text element (14,795 ASCII characters including the background, style and complete first prompt), and held the response open. After one second, Chrome 157.0.8103.80’s compositor screenshot was white. After sending the suffix and finishing the response, the same viewport showed the dark background and colored terminal. Capture the compositor directly for this test. Playwright’s ordinary screenshot waited on fonts and would have confounded the result.

Consequently there is no observed first-paint win from putting that prompt first in this delivery path. This test covers neither all progressive image formats nor GitHub’s CDN. Design the reveal relative to when the image can paint. A cached image may already have advanced its timeline when scrolled into view. If page-entry speed matters more than the continuous panel, compare a *separate complete* lightweight header against the single image in a rendered GitHub README on a cold throttled connection. Record first text paint from a filmstrip, total transferred bytes, cache state, seams at mobile widths and whether repeat visits replay. Keep the split only if visitors actually see useful content sooner.

**Pinball integration probe.** Following the upstream play link resolved to pinball.alula.me. Its HTML returned HTTP 200 and the response inspected had no X-Frame-Options or CSP frame-ancestors restriction. A temporary localhost page embedded that HTTPS URL. Chrome rendered the recognizable table in a 600 × 440 canvas and displayed “Player 1” and “Awaiting Deployment” after focusing it and sending start/plunger input. The surrounding upstream page supplied its own blue background and window chrome. The probe establishes framed startup and a visible table. Ball launch, scoring, mobile controls, touch focus, browser Back and compatibility with a restrictive iframe sandbox still need playtesting. A response header check alone would not establish even startup.

An outer link to the port is a viable fallback. Keep it visible beside the framed player because an iframe load event can fire even on failure. Cross-origin isolation of the document prevents restyling its internal canvas, reading score, drawing captured pixels to a readable canvas or reliably intercepting its Escape key through ordinary parent DOM access. Test any deliberate cross-window protocol against upstream support. [MDN iframe reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe) · [Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy)

The public demo demonstrates a delivery route. It supplies no evidence of a license for republishing original resource files, recordings or sprites in this repository. Recheck upstream before release. Keep attribution and a direct project link with the running game.

## Minecraft and Terraria follow-up

**Decision after testing.** Tobias selected official Minecraft Classic for the featured command. A browser release from Mojang gives immediate recognition and requires no local game data. Describe it as Mojang’s Classic browser release. The evidence for decompilation belongs to Space Cadet. Keep the official game on its own origin. [Mojang’s announcement](https://www.minecraft.net/en-us/article/embrace-past-minecraft-classic) · [Hosted Classic](https://classic.minecraft.net/)

| Cold startup sample | Finished HTTPS responses | Sum of reported response body sizes | Visible result |
| --- | ---: | ---: | --- |
| Mojang Minecraft Classic | 104 | 14,204,915 bytes | Terrain, held block, hotbar and version 0.0.23a_01 |
| alula Space Cadet | 6 | 4,806,192 bytes | Upstream Pinball application and table |

Method: Chrome 157, fresh browser context for each title, identical 800 × 620 cross-origin iframe on localhost, sample eight seconds after parent DOMContentLoaded. Summed Playwright request sizes for completed HTTPS responses, excluding headers. No failed requests observed. This single sample describes startup under these conditions. It does not measure time to playable input, peak memory, a full play session or bytes for all browsers. The document at classic.minecraft.net also returned 200 without X-Frame-Options or CSP frame-ancestors in the inspected response. Framed rendering was verified independently by screenshot. Only mounting the selected iframe keeps the other game’s cost at zero. A plain anchor in the SVG’s surrounding README markup costs neither game’s payload.

**Other Minecraft approaches.** CheerpJ’s Browsercraft is the closest match to literally running a JAR. The authors run Minecraft 1.2.5 unmodified with a WASM JVM and cap the demo at three minutes. That adds an EULA step and runtime without improving this handoff. TeaVM-based Eaglercraft ports also exist. Toolchain availability alone gives us no basis to redistribute Mojang’s code or textures. The official Classic page removes the need to assemble either runtime. [Browsercraft project demo](https://browsercraft.cheerpj.com/) · [TeaVM port project](https://github.com/EaglerPorts/in-20100223) · [Minecraft EULA](https://www.minecraft.net/en-us/eula)

**Terraria is genuinely feasible in a browser.** Mercury Workshop’s Terrarium decompiles a purchased desktop build and runs it with threaded FNA/.NET WebAssembly. Its build requires Terraria, and its hosting instructions require COOP and COEP response headers. The author describes the playable route for owners. This adds ownership and deployment constraints for a casual visitor. Revisit if Tobias specifically wants a bring-your-own-game experience. [Terrarium’s build and hosting requirements](https://github.com/MercuryWorkshop/terraria-wasm)
